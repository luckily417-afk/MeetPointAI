## 一、官方 API 能力核查结果

| 能力 | 接口 | 是否可用 | 备注 |
| --- | --- | --- | --- |
| 关键字 POI 搜索 | `GET /v3/place/text` | ✅ | 支持 `city`、`types`、分页；`count` 为总数 |
| 周边搜索 | `GET /v3/place/around` | ✅ | `radius` 上限 50000 m，`offset` 上限 25 |
| 多边形搜索 | `GET /v3/place/polygon` | ✅ | 顶点用 `\|` 分隔，建议 ≤10 个点；本程序用矩形分块（4 点） |
| 地理编码 | `GET /v3/geocode/geo` | ✅ | 返回 `formatted_address`、`adcode`、`level` |
| 逆地理编码 | `GET /v3/geocode/regeo` | ✅ | 返回 `citycode`、`adcode`、`formatted_address` |
| 驾车路径 | `GET /v3/direction/driving` | ✅ | `route.paths[0].steps[].polyline` |
| 步行路径 | `GET /v3/direction/walking` | ✅ | 结构同上 |
| 骑行路径 | `GET /v4/direction/bicycling` | ✅ | **v4 且使用 `errcode/errmsg` 结构**（非 `status/info`） |
| 公交路径 | `GET /v3/direction/transit/integrated` | ✅ | 必须传 `city`/`cityd`；中文城市名可能触发 `10021`，改用 citycode/市级 adcode |
| JS 地图 API | `https://webapi.amap.com/maps?v=2.0` | ✅ | 需 `window._AMapSecurityConfig`；QWebEngine 内 0.9 s 完成初始化 |
| DeepSeek 模型列举 | `GET /models` | ✅ | 零 token 成本，可用于鉴权探测 |
| DeepSeek 余额 | `GET /user/balance` | ✅ | 零 token 成本，可判定 `QUOTA_LIMITED` |
| DeepSeek 对话 | `POST /chat/completions` | ✅ | 支持 `response_format=json_object`、`reasoning_effort` |

实测注意点（已写入代码）：

1. **HTTP 200 不代表成功**：高德用 `status=1/0` + `infocode` 表达业务结果，必须解析；
2. **公交接口对极短行程无方案**（< 2.5 km），程序自动改用真实步行路线；
3. **推理模型会消耗大量思考 token**，`max_tokens` 过小会导致 JSON 被截断，因此默认 8000 且 `reasoning_effort=low`；
4. **瞬时 10021/10004/10041** 在高并发下偶发，做一次短退避重试即可，不应误判为 Key 失效。

## 二、分层架构

```
┌──────────────────────────── UI 层（PySide6, 主线程） ────────────────────────────┐
│ MainWindow：控制面板 / 地图视图 / 结果表 / 详情 / 三路状态胶囊 / 进度与日志           │
│ MapController + MapBridge：QWebChannel 双向通信；JS 调用统一排队回 GUI 线程          │
│ AsyncRuntime：asyncio 事件循环跑在后台线程，结果以 Qt 队列信号回到主线程             │
└───────────────────────────────┬──────────────────────────────────────────────────┘
                                │（纯 Python 调用，无 Qt 依赖）
┌───────────────────────────────▼──────────────────────────────────────────────────┐
│ 编排层 algorithms/pipeline.py                                                     │
│  校验请求 → 分块检索（candidates）→ 几何硬过滤 → A/B 路线 → AI 排序/校验 → 二次复验  │
│  失败路径：AI 无效/不可用 → 规则排序（ranking）；无结果/服务故障 → 明确错误           │
└──────┬───────────────────────┬────────────────────────┬───────────────────────────┘
       │                       │                        │
┌──────▼──────┐        ┌───────▼────────┐       ┌───────▼─────────┐
│ services    │        │ geometry       │       │ monitoring      │
│ amap_web    │        │ crs / regions  │       │ health + backoff│
│ deepseek    │        │ Shapely 判定    │       │ 9 状态分类       │
│ http_client │        │ 分块覆盖算法     │       │ 业务回写         │
└──────┬──────┘        └───────┬────────┘       └───────┬─────────┘
       │                       │                        │
┌──────▼───────────────────────▼────────────────────────▼─────────────────────────┐
│ storage/db.py（SQLite）：kv_cache / health_log / sessions / app_settings          │
└──────────────────────────────────────────────────────────────────────────────────┘
```

设计原则：

- **UI 不含业务判断**：范围过滤、AI 校验、降级决策全部在纯 Python 层，可被测试脚本直接复用；
- **服务层无状态**：`AMapWebService` / `DeepSeekService` 只负责协议与错误分类；
- **可测试性**：几何、排序、校验、健康分类、主流程均有独立测试，主流程用假客户端注入。

## 三、关键算法

### 1. 圆形区域判定

```
contains(p) = haversine(center, p) <= radius + ε      # 球面距离，边界算在内
```
绝不使用「经纬度差 × 常数」近似。

### 2. 多边形区域判定

1. 以顶点质心为原点建立局部等距投影（`x = Δlng·R·cos(lat₀)`，`y = Δlat·R`）；
2. 在投影平面上构造 Shapely `Polygon`；
3. 有效性检查：顶点数 ≥3、去重、`is_simple`（自相交检测）、面积阈值；
4. 判定使用 `prepared.covers(Point)` —— **边界算在内**，且凹多边形天然支持。

> 局部投影在 50 km 内误差 < 0.1%，远小于 POI 检索半径；距离度量始终由 haversine 负责。

### 3. 大区域分块检索

- 圆形：按网格布置子圆，`cell_r = clamp(target/2, 300, 2000)`，间距 `1.4·cell_r`（< √2·r，保证覆盖）；
- 多边形：bbox 投影后切矩形网格，丢弃与多边形无交集的格子，逐格调用 `place/polygon`；
- 每块内分页（`offset=25`，最多 4 页），全局调用预算 `max(8, min(64, 2×块数))`；
- 去重：POI ID + (名称, 50 m 网格) 双键；
- 截断：按到区域中心的距离排序后取前 `max_candidates` 做路线规划。

### 4. 推荐排序（取消公平性评分）

| 模式 | 依据 |
| --- | --- |
| 最短总通勤时间 | `duration_a + duration_b` 升序（换乘、长距离步行有小权重惩罚） |
| 最少换乘 | `transfers_a + transfers_b` 优先，再按总时长 |
| 指定场所类型优先 | 类型码匹配者获得显著加分，再按总时长 |
| AI 综合推荐 | 交给 DeepSeek，Python 只校验与复验 |

不可达候选（任一侧无路线）一律排到最后，且不计入最终展示。

## 四、九步主流程（需求 4.3）

| 步 | 实现位置 | 说明 |
| --- | --- | --- |
| 1 | UI：`_on_circle_changed` / `_on_polygon_closed` | 用户绘制区域，立即做几何有效性校验 |
| 2 | `pipeline._validate_request` | 取区域几何，校验模式与几何是否匹配 |
| 3 | `candidates.discover_pois` | 高德分块 + 分页检索真实 POI |
| 4 | `candidates.discover_pois` 末段 | `region.contains()` 精确过滤（硬约束） |
| 5 | `candidates.plan_routes` | 每个候选规划 A→POI、B→POI 真实路线（限并发 4） |
| 6 | `pipeline._rank` | 只把通过校验的候选（默认 12 个）交给 DeepSeek |
| 7 | `deepseek.chat_json` | 强制 JSON，仅返回 `poi_id` 与理由 |
| 8 | `ai_validator.validate_ai_payload` | ID 存在性、重复、坐标断言、区域内外复验 |
| 9 | `pipeline.run` 收尾 | 再复验一次区域，通过后才生成推荐并落库 |
